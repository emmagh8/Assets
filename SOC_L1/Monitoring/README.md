# SOC Team Internals

## Overview

In the previous section, I learned the core responsibilities of a SOC analyst, including alert triage, classification, and escalation. This section focuses on how SOC teams operate internally during alert handling, investigation workflows, SIEM usage, and SOC performance measurement.

The main responsibility of an L1 SOC analyst is to determine whether an alert represents:

- **True Positive (TP)** → real security threat  
- **False Positive (FP)** → benign activity wrongly detected as malicious  

This decision-making process is called **triage**.

---

## What is Triage?

Triage is the process of analyzing and prioritizing security alerts to determine whether they represent a real threat or normal behavior.

Not every alert is malicious. Many are false positives generated by detection rules.

The goal of triage is to:
- Identify real threats quickly
- Reduce alert noise
- Improve SOC efficiency

---

## Why Do We Need Triage?

Modern systems generate millions of logs daily from:

- Endpoints
- Servers
- Firewalls
- Applications
- Cloud services
- Network devices

It is impossible for humans to manually analyze all logs.

To solve this, organizations use centralized security platforms to:
- Collect logs
- Normalize data
- Correlate events
- Generate alerts

---

## Security Monitoring Technologies

### EDR (Endpoint Detection and Response)

Monitors endpoint behavior such as:
- Process execution
- File changes
- User activity

Examples:
- Microsoft Defender for Endpoint
- CrowdStrike Falcon

---

### NDR (Network Detection and Response)

Monitors network traffic such as:
- DNS requests
- Connections
- Data transfers
- Suspicious IP communication

---

### SIEM (Security Information and Event Management)

A SIEM centralizes logs from multiple sources and correlates them using detection rules.

Examples:
- Splunk
- Microsoft Sentinel
- IBM QRadar
- Elastic Security
- Wazuh

## SOC Alert Structure

| Property | Description |
|----------|-------------|
| Alert Time | When the alert was generated |
| Alert Name | Summary of detected activity |
| Alert Severity | Risk level of the alert |
| Alert Status | Current workflow state |
| Alert Verdict | True Positive / False Positive |
| Alert Assignee | Responsible analyst |
| Alert Description | Explanation of detection logic |
| Alert Fields | Technical evidence (IP, user, hostname, etc.) |

---

## Alert Prioritization

SOC analysts prioritize alerts using:

### 1. Severity
- Critical
- High
- Medium
- Low

### 2. Time
Older alerts are usually handled first to reduce attacker dwell time.

---

## SOC Alert Handling Workflow

1. Assign alert
2. Set status → **In Progress**
3. Read alert name & description
4. Collect key information (user, IP, host)
5. Investigate using SIEM / EDR
6. Determine verdict
7. Escalate if needed
8. Document findings
9. Close alert

---

## 5W Reporting Model

SOC reports are structured using the 5W model:

### Who
- User
- Hostname
- IP address

### What
Actions performed:
- Login attempts
- File execution
- Downloads

### When
Timeline of events

### Where
Systems, devices, or IPs involved

### Why
Reasoning behind the final verdict (most important part)

### Example

> At 08:00 AM, user *mr.jams* accessed a phishing site from Laptop-HR-01.  
> At 08:02 AM, the user downloaded a file named *mimikatz.exe*.  
> SIEM flagged the activity as malicious due to credential dumping behavior.  
> The alert was escalated to L2.

## Investigation

Investigation is the most technical phase of SOC work.

Steps:

1. Identify affected user / system
2. Understand suspicious activity
3. Analyze surrounding events
4. Correlate evidence from SIEM / EDR
5. Validate using threat intelligence

Goal:
→ Determine if activity is malicious or legitimate

---

## SOC Workbooks

Workbooks (Runbooks / Playbooks) are structured guides that help SOC analysts investigate alerts consistently.

### Workflow Example

1. Identify user & asset
2. Check identity inventory
3. Check asset inventory
4. Validate IP reputation
5. Check VPN / Proxy / TOR usage
6. Analyze timeline in SIEM
7. Compare with user behavior baseline
8. Determine verdict
9. Escalate if necessary

### Network Visibility

Typical network segments:

- Database subnet: `172.16.15.0/24`
- VPN subnet: `10.10.0.0/16`
- Office subnet: `172.16.23.0/24`

Unusual traffic outside expected segmentation may indicate:
- Compromise
- Lateral movement
- Unauthorized access

## SOC Performance Metrics

SOC teams measure analyst efficiency using metrics.

| Metric | Formula | Description |
|----------|---------|-------------|
| Alert Count (AC) | Total alerts received | Workload measurement |
| False Positive Rate (FPR) | FP / Total Alerts | Quality of detection |
| Alert Escalation Rate (AER) | Escalated / Total Alerts | Escalation efficiency |
| Threat Detection Rate (TDR) | Detected Threats / Total Threats | Detection effectiveness |

### Typical Ranges
- 5–30 alerts/day per L1 analyst
- 10–75% false positive rate
- <50% escalation rate
- ~100% detection target
